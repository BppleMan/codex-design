# 需求判断的行为演练

日期：2026-10-09。目标：检查 Skill 是否根据需求与上下文选择推进方式，而非默认要求用户说出 grill-me 或走完访谈。

评估者为未继承本次修改讨论的独立 agent，读取待测 Skill 与所需引用，分别处理独立请求；没有给出预期答案或告知待修问题。范围限于回复、提问决策和下一步工具路径，不实际创建原型或向用户发问。

| 用户请求 | 实际决策 |
| --- | --- |
| 个人 macOS 待办，三个视图及新增、完成、恢复已明确，先用 mock | 直接设计，标记可逆的未定状态规则，没有追加访谈 |
| 只有“想做个效率工具” | 询问具体使用情境和希望改善的结果，没有自行套用待办模板 |
| 设备借用流程已明确，仅缺少谁能修改他人记录的规则 | 只澄清编辑权限，没有重问字段和主流程 |
| 详细待办需求同时明确“先 grill-me” | 针对“今天”的语义和跨日行为深入追问，没有跳过，也没有重复已知信息 |
| 已确认原型，只把保存按钮改为“保存草稿” | 选择定位并局部修改，不重启产品访谈或初始化新底座 |
| 植物养护应用，“按你的判断先做一版，暂时别问问题” | 以显式假设直接设计，没有提问或扩展到真实服务 |
| “效率工具”用户下一轮已补全个人桌面待办的路径和排除范围 | 停止追问，开始原型；没有为了凑轮数继续访谈 |

需要提问的案例处于 Default 模式：评估者选择普通 final 消息等待下一轮，没有调用仅限 Plan 的同步工具，也没有使用异步提问或轮询。这个模式限制不改变是否需要澄清的产品判断。

本次观察支持这些场景下的决策分流与回答后的收敛，不代表所有未来任务都已验证，也不证明原型生成、真实提问窗口或浏览器流程完成。结构与链接校验另行执行，不用关键词匹配冒充行为测试。
