# 需求判断的行为演练

日期：2026-10-09。目标：检查 Skill 是否根据需求与上下文选择推进方式，而非默认要求用户说出 grill-me 或走完访谈。

评估者为未继承本次修改讨论的独立 agent，读取待测 Skill 与所需引用，分别处理独立请求；没有给出预期答案或告知待修问题。范围限于回复、提问决策和下一步工具路径，不实际创建原型或向用户发问。

| 用户请求 | 实际决策 |
| --- | --- |
| 个人 macOS 待办，三个视图及新增、完成、恢复已明确，先用 mock | 直接设计，标记可逆的未定状态规则，没有追加访谈 |
| 只有“想做个效率工具” | 询问具体使用情境和希望改善的结果，没有自行套用待办模板 |
| 设备借用流程已明确，仅缺少谁能修改他人记录的规则 | 只澄清编辑权限，没有重问字段和主流程 |
| 详细待办需求同时明确“先 grill-me” | 针对“今天”的语义和跨日行为深入追问，没有跳过，也没有重复已知信息 |
| 已确认原型，只把保存按钮改为“保存草稿” | 选择定位并局部修改，不重启产品访谈或初始化新底座 |
| 植物养护应用，“按你的判断先做一版，暂时别问问题” | 以显式假设直接设计，没有提问或扩展到真实服务 |
| “效率工具”用户下一轮已补全个人桌面待办的路径和排除范围 | 停止追问，开始原型；没有为了凑轮数继续访谈 |

演练当时，评估者因一个同步工具的模式限制选择了文字兜底，未检查其他原生表单路径。这暴露了旧版 Skill 对工具返回方式的过度限制；这部分结论已纠正，不能据此声称 Default 模式没有原生提问能力。上述演练只验证是否需要澄清及何时收敛，没有实测原生窗口的打开、等待和用户回执。

本次观察支持这些场景下的决策分流与回答后的收敛，不代表所有未来任务都已验证，也不证明原型生成、真实提问窗口或浏览器流程完成。结构与链接校验另行执行，不用关键词匹配冒充行为测试。

## 原生表单回执实测

在本轮 Default 会话中，实际调用 `request_user_input_async` 提交一条交互验证问题，工具返回 accepted。随后保持当前轮等待：第一次 `clock.sleep` 到时没有答案，未发送 final；第二次等待被新用户输入中断。收到了与这份表单对应的 `send_user_message_question_reply`，并按回执内容继续原任务。

用户在回答中区分了两件事：此前 FAB 的原生窗口能持续显示并等待；另一个使用旧 Skill 的新项目连窗口都没有弹出。用户没有明确确认本轮窗口的持续视觉表现，因此本次可证明的是当前会话的表单调用、等待和回答回传闭环，不将其夸大为所有环境或窗口视觉状态均已验证。

这次修正删除了“禁止异步工具”的 Skill 附加限制，改为按当前工具契约选择原生表单，并在异步返回时保持可中断等待。某个同步 API 受模式限制，不能推出当前模式没有原生提问 UI。先前首轮演练中的文字兜底选择不再作为该限制的依据。
