# Bridge Studio 案例：用用户反例补齐原型边界

这份记录说明方法如何形成，不把本项目的业务规则变成通用模板。
证据范围仅限本次对话、独立 Web 原型及其检查记录。

## 证据标签

- **观察事实**：用户明确提出、纠正或确认的要求，以及实际实现和验证的行为。
- **合理推断**：从反例和操作反馈推导出的建模方法；用于提出下一步设计，不冒充已确认规则。
- **未知**：缺少对照、正式实现或宿主验证的结论，必须继续保留边界。

## 从初版到 V2：改变了什么

1. **观察事实**：用户要求独立 Web 项目，使用 mock 数据和虚假业务功能，先在内置浏览器里操作，再决定如何落地。
   这授权的是可交互原型；不等于授权提前接入真实账号、支付、服务或正式项目。
2. **观察事实**：初版已有两端外壳、模拟连接和日志，但功能对象与页面层级仍需要用户指导。
   有按钮、有成功状态，并不证明产品结构已经完整。
3. **观察事实**：用户用同一文件同时在 Figma Desktop 和 Web 打开插件的场景，挑战了“文件就是连接”的假设。
   这个反例推动了文件、插件实例、连接配置和运行会话的区分。
4. **观察事实**：用户随后提出 Desktop 也可能通过局域网地址访问。
   这推动了 Bridge 类型与部署位置分离，以及多个 Desktop 目的地的独立审批和运行状态。
5. **观察事实**：V2 明确为先创建连接，列表直接展示详情，点击某条连接后进入仅属于它的最近活动。
   变化来自用户对操作和归属的纠正，不能只理解为换一套卡片样式。

## 可迁移方法一：让反例改变对象模型

- 先理解用户的想法、目标和具体情境，再分轮追问以澄清对象、操作和约束；现有实现仅在相关且可用时作为证据。
- 提问不是走形式：用当前模式允许的同步原生提问工具，真正等待其返回答案。用户已明确纠正 harness loop 不支持异步提问；同步工具不可用时改用普通消息等待下一轮，不调用异步工具或用轮询模拟阻塞。
- 用户提供反例时，先问自己“哪个对象被错误合并”，而不是立即加一个补丁按钮。
- 本例把“一份文件”等同于“一个插件实例”，会把同文件不同窗口的选区、活动和授权混在一起。
- 本例把“Desktop 类型”等同于“localhost”，会让退出本机应用错误地影响局域网里的另一台电脑。
- 本例把“已授权”等同于“希望自动连接”，会在用户主动断开后又擅自重连。
- 本例把“有效订阅”等同于“服务可达”，会把服务故障误报成没有订阅。
- 将反例改写为可操作场景，并把它加入 mock 状态转换；后续改版必须仍能复现。
- **合理推断**：复杂度往往藏在对象之间的归属关系，而不是功能名称的数量。
- 可执行结论：对每次重要反例，核对受影响的归属与行为维度；身份、授权、路由、生命周期和记录归属是本例的检查方向，不是所有产品的必填功能。

## 可迁移方法二：让一份 Web 原型暴露跨端遗漏

- 同一个 Web 项目中的多个模拟器共享必要的 mock 状态，才能演示一端操作如何影响另一端。
- 共享模拟状态不意味着共享业务身份：不同目的地仍有自己的审批、会话、离线状态和历史。
- 本例左侧发起连接，右侧对应 Desktop 收到申请；接受后两端同步更新。
- 本例切换正在模拟的 Desktop，审批与日志也必须跟随目的地切换。
- 在真实产品外提供 tweak 场景控制，主动制造空状态、未授权、故障、恢复和多实例情况。
- tweak 是评审工具，不应作为正式产品功能混进模拟窗口。
- 只展示默认成功路径，会漏掉授权弹窗取消后无法继续、断线后指令错误改投等问题。
- 不同故障要能独立触发，否则“全断开”的演示无法检验依赖边界。
- 保留原生操作：用户应能点、滚动、输入、拖动，并看到明确结果，而不只是看静态页面。
- **合理推断**：跨端联动和可控异常能把隐含需求变成可讨论的具体界面。
- 可执行结论：先做能暴露产品取舍的场景，再根据用户反馈补齐；不要求机械穷举所有状态。

## 可迁移方法三：使用现成评审能力，准确解释验证结果

- 在 Codex 内置浏览器中评审时，使用 Codex 的内置批注能力，不在原型里另造一套批注产品。
- 本次早期自行实现标注按钮、编号和存储，是不应固化的反例。
- 用户说“直接标注然后修改”，并不自动意味着 Web 项目需要新增标注系统。
- 按批注所在的实际页面和对象理解反馈；必要时先复现该界面，避免改错范围。
- 将用户确认过的方向写入适用的项目或原型指引，避免下一轮用通用建议覆盖它。
- 功能测试通过、浏览器操作有效、用户视觉确认，是三种不同证据。
- 本例曾用预留 scrollbar gutter 消除宽度跳动，但用户否定了左右视觉留白不对称。
- 数值“稳定”没有满足用户的完整目标；后续改为不占布局宽度的 overlay 滚动条。
- 验证应覆盖用户指出的性质：溢出前后宽度、左右留白、实际拖动及输入行为。
- 不把测试通过、截图生成或本地可运行写成“用户已经满意”或“正式宿主已经验收”。

## 视觉处理的边界

- **观察事实**：用户认为本次的颜色和信息密度不错；本例并非每一轮都需要重新探索视觉方向。
- 好看的初稿有价值，但不应因此把当前配色、字体、布局密度写成默认审美答案。
- 视觉精调必须被明确考虑：先确认该项目的方向，再检查配色、密度、层级和关键状态；已有明确认可的部分可以保留，无需强行改换风格。
- 保留已经认可的视觉部分，优先修改用户指出的功能结构或交互问题。

## 不得硬编码的项目特例

- Figma 与 macOS 双模拟器、左窄右宽双栏，是本项目的演示方式；其他任务可能只有一个界面。
- Desktop / Official / Selfhost、只读能力、订阅门槛及具体配对规则，是本项目业务假设。
- targetId、插件实例、多个目的地的具体字段名称，不是所有原型必须采用的数据结构。
- 紫色视觉、卡片层级和当前信息密度，不是通用主题规范。
- React 原型后续转译 Angular，是本项目技术安排；应根据目标项目选择实现和交付路径。

## 尚不能声称的结论

- **未知**：用户更换模型后，后续设计变得更清晰；没有对照证据证明改进由模型更换单独造成。
- **合理推断**：新增反例、连续反馈、已有原型和多轮实现共同提供了更多约束。
- **未知**：原型尚未完成正式业务落地，不能据此证明所有 mock 行为都能在真实宿主中直接实现。
- 后续 1:1 转译仍需用户确认定稿，再核对真实 API、权限、网络和宿主限制。
- 可执行结论：复用的是收敛问题、构建交互和验证反馈的方法，不是复制本例的业务或宣称。
