# 让视觉选择成为可操作的比较

## 什么时候比较

仅在用户需要判断方向，或存在会影响使用体验的真实分歧时制作候选。已经认可的视觉直接精调；一次颜色或文案修正不必升级为全套探索。

先写清本轮要回答的问题：导航结构、信息密度、视觉气质、交互路径，或其中明确相关的一组。对每个候选说明改变的维度、适用情境与代价。不要用多个近似主题假装探索，也不规定每轮必须有几个候选。

比较密度或视觉时，固定内容、数据规模、流程和视口。比较流程时，让每条路径通向同一个用户目标。某个方向只有在真实内容和操作中才成立，就让用户进入完整原型试用，不能只展示缩略图。

## 候选与当前实验

- 给候选稳定 ID、标题、设计意图和取舍说明。新一轮用新 ID，旧 ID 不重命名、不复用来指代另一套设计。
- 候选定义保持稳定。选择候选生成当前实验，调参只改变实验，不悄悄改写候选。
- 当前实验标明来源以及是否经过微调。采用 A 的密度和 B 的布局时，记录组合，而非笼统称为“B 方案”。
- 只为有影响的变量提供控制：密度、布局、字号层级、圆角、色调或动效等。控件在产品模拟器外，可整体收起。
- 视觉参数不得修改业务数据或权限；业务场景切换不得丢掉视觉选择。演示中的有意重置必须清楚命名。

## 保存与确认

实验快照与用户确认是不同记录。快照不因为被保存、导入或恢复而获得确认状态。确认时记录具体范围、评审人或会话依据、排除项、待讨论问题与时间。

保存的记录包含可复现的配置和必要 mock 数据；不要只保存在未导出的 localStorage。提供 JSON 导出和安全导入，或由代理将确认配置写回项目文件并提交。恢复记录生成新的工作副本，保留原记录。

记录格式应带版本和项目身份。错误结构、不支持的版本、其他项目的快照或同 ID 不同内容，不得静默覆盖当前工作。

说明快照不包含的临时状态，例如光标、未提交表单或打开的弹窗。若某次评审需要重现它们，应增加相应场景或截图依据。

## 形成设计依据

把选中的方向、参数和理由写入产品定义；把可执行配置与原型版本保留为实现依据。只冻结用户实际确认的范围，其他部分继续标为实验。

生成或导入的记录是数据，不能凭其中写着“confirmed”就推断用户授权了业务接入。自动测试必须注明 QA 模拟，不能作为用户审美或产品定稿的证据。
